# Shared-prefix candidate encoding: evaluate each state/question prefix once

## Problem

Every candidate answer is encoded as `prefix + candidate_suffix`, where the prefix is the
state plus the question text and is byte-identical for all candidates of a question:

```python
# scripts/predict_toy_decisions.py
prefix = sum([tokenizer.encode(t, add_special_tokens=False) for t in segments], [])
leaves = [prefix + tokenizer.encode(f"Candidate:\n{t}\nDecision:", ...) + [eos] for t in texts]
```

`DecisionModel.encode_leaves` flattens those paths into one padded batch and runs the
backbone once, so a question with `K` candidates and a `P`-token prefix evaluates the
prefix `K` times. Measured on the repository's own artifact
(`research/dynamic_candidates_v2.json`: 346 paths, 16,777 path tokens, 50-token paths),
about 82% of that forward is duplicated prefix. The repository already documented this
(`docs/TYPESAFE_CONTRACT.md`, `scripts/train_toy_decisions.py` header) and every prediction
response carried `"prefix_sharing": false`.

## Change

Two-stage encoding, with an optional encoder that the existing forward can use:

1. **Prefix stage** — encode the prefix alone as one row with `use_cache=True`; keep the
   keys and values.
2. **Suffix stage** — run only candidate suffix tokens against a cached prefix, with an
   additive mask `(rows, 1, S_max, P + S_max)` that lets suffix query `P + j` attend to
   prefix positions `0..P-1` and its own suffix `0..j`, never another candidate's suffix.
   Position ids continue at `P` and `cache_position` is passed explicitly so the supplied
   mask is used as-is.

The prefix keys/values reach the model through a zero-stride `expand`, so they are stored
once regardless of candidate count. Candidate rows are processed in optional chunks to
bound peak memory.

## Equivalence

For candidate `c`, the reference reads the final hidden state of `prefix + s_c` under a
causal mask. The shared path presents the same keys, values and query positions, so the
attention inputs are identical and only softmax reduction order differs.

Three levels of evidence, weakest to strongest:

1. **Tiny real Qwen3 backbone, CPU float32** — mixed candidate counts and widths, Boolean
   single-path questions, chunked encoding, gradients through the shared path.
2. **Full 28-layer Qwen3-0.6B backbone in float32/SDPA** — drift a few `1e-6`
   (`test_real_model_equivalence_and_reduction`).
3. **The published `unified-games-v1` decision checkpoint** (`ReleasedCheckpointTests`),
   gated on the released weights SHA256 and skipped when absent. The load is strict
   (zero missing or unexpected tensors) and the measured result is:

   | Quantity | Result |
   | --- | --- |
   | logits, max absolute difference | `9.54e-07` |
   | published probabilities, max absolute difference | `2.09e-07` |
   | `valid` mask | bitwise equal |
   | decision argmax | identical for every question |
   | leaf tokens | 2.275x fewer |

   The tokenizer loader normalizes one upstream export detail: transformers 4.51 wrote
   `extra_special_tokens` as a list, which 4.57 rejects. The release's `tokenizer.json` is
   byte-identical to the base model's (same SHA256), so only that metadata field is
   rewritten, in a temp copy.

A dtype note that matters for reviewing the tests. With `attn_implementation="eager"` in
bfloat16 this model already differs from *itself* by ~`5.5e-2` when only the attention
implementation changes, so bf16 comparisons are only meaningful between matched
implementations. The tests therefore pin three separate statements: float32 absolute drift
(a few `1e-6`), SDPA+bfloat16 bit-identity, and bf16 **autocast** relative drift, which is
the precision the service runs. A wrong mask moves logits by order `1`, far above every
threshold used, so a broken mask fails these tests rather than slipping through.

Two guard rails come with this. A supplied 4-D mask is passed through by transformers with
no causal safety net, so `assert_supported_attention` restricts the backend to eager or
SDPA (Flash-Attention 2 rejects a float 4-D mask) and `assert_supported_cache` rejects
static, sliding-window and hybrid caches whose in-place writes would disturb the broadcast
prefix. The broadcast itself uses a zero-stride view; `test_chunked_suffix_encoding_matches_unchunked`
is what actually proves the prefix survives repeated chunked forwards.

Prefixes are **never shared across questions** unless the prefix tokens and every candidate
suffix are identical (`covered_by`), which makes them the same cached tensors; no fuzzy
matching. An authored `prefix_length` (the state+question text) bounds the split so the
prefix cannot absorb candidate text; without it the whole observed common run is shared and
reported under `unverified_split_questions`.

## Measured effect

Structural accounting (hardware independent, from `SharedPrefixPlan.accounting()`):
prefix token evaluations fall from `K * P` to `P`, and batch padding disappears.

`results/shared_prefix_benchmark.json`, real checkpoint, MPS, float32, SDPA, two states:

| Candidates | Leaf tokens ref → shared | Token reduction | Wall clock | Speedup | Max drift |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 4 | 320 → 156 | 2.05× | 351 ms → 170 ms | 2.07× | 1.5e-06 |
| 16 | 1312 → 472 | 2.78× | 1378 ms → 440 ms | 3.13× | 1.6e-06 |
| 64 | 5248 → 1784 | 2.94× | 5915 ms → 1261 ms | 4.69× | 2.0e-06 |

**Honest caveats, also in the doc:** token reduction is not wall-clock reduction, because
the suffix pass still attends over the cached prefix, so measured speedup trails the token
ratio. The decisive structural win is memory, `O(K * W)` → `O(P + chunk * S_max)`, which is
what makes large candidate sets feasible rather than merely faster. Timings are machine
specific and live in the artifact, never asserted as constants.

## Compatibility

* `DecisionModel.forward(examples, pad_token)` still returns `(logits, valid)` and still
  uses the reference encoder by default; `test_reference_path_is_unchanged_by_the_refactor`
  asserts the split methods produce bit-identical output to the historical combined path.
* `DecisionPredictor.predict` defaults to `prefix_sharing=False`, so existing responses
  keep their recorded `prefix_sharing: false` semantics. When enabled, the response adds
  `execution.sharing.accounting` and `execution.tree_attention`.
* `scripts/train_unified_games.py` and `scripts/train_pipeline_decisions.py` call
  `model(group, pad_token)` unchanged; training keeps the reference layout in this PR.
* With sharing enabled, `batch_questions` no longer partitions backbone work because each
  question owns an independent cache; this is documented and tested.
* `execution.prefix_sharing` / `execution.tree_attention` now report **what ran**, not what
  was requested. A batch with no shareable prefix falls back inside `DecisionModel.forward`,
  and the response then keeps `prefix_sharing: false`, sets
  `prefix_sharing_requested: true` and adds `sharing.fallback_reason`.
* Two questions that are byte-identical (same state, question and candidate set — the common
  case of a repeated action set across states) are an exact cache reuse, reported under
  `accounting.reused_questions`; they cost no prefix encode and no suffix encode.

## Tests

`python3 -m pytest scripts/ -q` → **444 passed, 6 skipped** on this branch versus
**372 passed, 6 skipped** on `618cea6`; the six skips are the pre-existing optional-artifact
skips, and none of the new tests skip when a checkpoint is present. The anchors resolve local
checkpoints by walking up from the checkout (or `NANOJEV_CHECKPOINT_DIR` /
`NANOJEV_RELEASE_DIR`), so they run in a linked worktree instead of silently skipping.

Two things the tests do that are worth reviewing on their own:

* **An independent oracle.** `test_reference_path_is_unchanged_by_the_refactor` compares
  `forward` against the helpers it now calls, so a defect moving both together would pass it.
  `test_refactor_is_bit_identical_to_the_pre_refactor_release` re-implements the released
  `618cea6` `forward` body verbatim and asserts `torch.equal` instead.
* **Mutation testing, not an assertion about mutation testing.** Four defects were injected
  and run against uniform *and* ragged candidate widths. Cross-row leakage (`8.1e-04` /
  `1.9e-03`), invisible prefix (`7.0e-02` / `6.9e-02`) and position ids restarting at zero
  (`3.9e-02` / `5.8e-02`) are all caught in both. A global causal mask is **not** a defect
  here — for a real query `P+q` it permits exactly prefix `0..P-1` plus suffix `0..q`, the
  same columns as the intended mask, differing only for padding queries whose outputs are
  never read. That is now documented on the mask builder so nobody "fixes" one into the
  other, and pinned by `test_global_causal_mask_is_equivalent_for_real_queries`. This is a
  different mutation from the one `research/tree_attention_check.json` flags at `0.304`,
  which is why per-variant measurement was needed.

No existing test was modified except where it encoded an assumption the reference actually
contradicts — for example the reference pads every path in the flat batch to one width, so
`reference_leaf_tokens` is `width * paths`, not the raw leaf-token sum.

## Out of scope

* Enabling sharing inside the training loop (changes the update path; deliberately separate).
* Cross-question prefix reuse.
* The set-attention head is still `O(K^2)`; at very large `K` it becomes the next bottleneck.
